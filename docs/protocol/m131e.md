# M131E: 1xDial w/ IPS (PID 0x0206)

## Descriptor [hw]

| report | direction | size |
| --- | --- | --- |
| input 1 | in | 63 bytes |
| output 2 | out | 319 bytes, the same as M4315, so images likely use the same chunking |
| feature 3 | out | 31 bytes |
| features 0x47–0x4e | get | 31 bytes each |

## Known commands

| bytes | meaning | source |
| --- | --- | --- |
| feature `03 49 01` | software mode on (`00` = hardware mode) | [up] cooltek-sdk |
| get feature 0x4a | serial number, `4a <len> <ascii>` | [up] cooltek-sdk |

## Vendor SDK [hw]

`CoolTEK_SDK_CM_M131E_V03.02.00.dll` exports the same API shape as the 15-key module's DLL, but has no per-button functions:

- `Set_Sw_Mode`, `Adjust_Backlight`, `Get_Backlight`
- `Display_Picture_On_Screen`, `Display_Color_On_Screen`, `Save_Screen_Picture`
- `Get_Device_Infos`, `Get_FW_Infos`, `Get_Config_Infos`, `Get_Config_Data`, `Get_Animation_Infos`
- `Check_Rcv_Data`, which handles input

There are no LED functions, so the Dial probably has no RGB.

## Get features [hw]

`hubdeck probe info dial` on a module with serial `MHDD01AA22…` and firmware 01.00.04.00:

| id | reply | meaning |
| --- | --- | --- |
| 0x47 | `0f df 07 5a 29 "01.00.00.00"` | firmware info (bootloader?) |
| 0x48 / 0x49 | `0f 26 a0 d8 0a "01.00.04.00"` | firmware info (MasterHUB reads 0x48, like M4315's 0x38) |
| 0x4a | `14 "MHDD01AA221252301064"` | serial number |
| 0x4b | `0b 14 00 00 00 f0 00 f0 00 01 f0 f0` | device info, see below |
| 0x4c | `01 64` | backlight = 100 |
| 0x4d | `11 c3 07 4c 0d 95 7c 03 00 …` (repeated) | animation info (layout unknown) |
| 0x4e | `10 92 75 5b 0f 74 00 00 00 …` (repeated) | config info (layout unknown) |

Device info lined up against M4315's 0x3b (`0b 14 03 05 0f e0 01 10 01 01 48 48`):

| byte | M4315 | Dial | meaning |
| --- | --- | --- | --- |
| 1 | `14` | `14` | ? |
| 2–3 | `03 05` | `00 00` | rows, columns of buttons |
| 4 | `0f` | `00` | button count |
| 5–6 | `e0 01` = 480 | `f0 00` = 240 | screen width (u16 LE) |
| 7–8 | `10 01` = 272 | `f0 00` = 240 | screen height (u16 LE) |
| 9 | `01` | `01` | ? |
| 10–11 | `48 48` = 72×72 | `f0 f0` = 240×240 | button image size |

**Screen: 240×240 [hw]** (round panel). The get IDs mirror M4315's shifted by +0x10 [hw].

## Input [hw]

Channel 0 uses tag **`0x44`**, which is M4315's `0x34` + 0x10.

| report | meaning |
| --- | --- |
| `01 44 03 00 \| 03 01 00` | turned one detent **clockwise** |
| `01 44 03 00 \| 03 01 01` | turned one detent counter-clockwise |
| `01 44 03 00 \| 04 01 01` | pressed |
| `01 44 03 00 \| 04 01 00` | released |

Note that the Dial's direction byte is the opposite of the knobs' (`00` is clockwise here). Inputs arrived while MasterHUB was running, so its software mode was already on.

## Commands from the vendor DLL [dll]

These were found by disassembling `CoolTEK_SDK_CM_M131E_V03.02.00.dll`, an incremental-link debug build. Every `*_CM_M131E` export is a wrapper around a generic `*_CM` function, which fills a buffer and calls the DLL's bundled hidapi. Feature reports are 32 bytes.

| function | report | bytes |
| --- | --- | --- |
| `Set_Sw_Mode_CM` | feature | `03 49 <mode>` (matches upstream) |
| `Adjust_Backlight_CM` | feature | `03 44 <0-100>` (rejects > 100) |
| `Display_Color_On_Screen_CM` | feature | `03 46 R G B` |
| `Display_Picture_On_Screen_CM` | output | `02 45 <chunk u16> <len u16> 00 <last> <≤312 B>`, then repeated (chunk size = report length − 8) |
| `Get_Config_Data_CM` | output | `02 48` / `02 49` |
| ⛔ `Set_Serial_Number_CM` | feature | `03 45 …` |
| ⛔ `Test_FW_Recovery_Process_CM` | feature | `03 48` |
| ⛔ `Save_Factory_Data_CM` | feature | `03 4b` |
| ⛔ `Test_Factory_Reset_Process_CM` | feature | `03 4c` |
| ⛔ `Test_Animation_Recovery_Process_CM` | feature | `03 4d` |
| ⛔ `Update_FW_by_type_CM` | output | `02 44 …` |
| ⛔ `Save_Screen_Picture_CM` | output | `02 47 …` (stores the picture in flash) |

**Picture data.** If the data starts with `BM`, the DLL treats it as a BMP: it keeps the 54-byte header, drops row padding and flips the rows to top-down 24-bit pixels. Anything else (e.g. a JPEG) is sent as-is. Which formats the firmware accepts is to be confirmed on hardware.

⛔ = on hubdeck's denylist.

## Confirmed on hardware [hw]

These were tested with MasterHUB fully closed (`hubdeck probe …`):

- `03 49 01` software mode on, and `03 46 ff 00 00` shows solid red.
- `03 44 <n>` sets the backlight: 10 → visibly dark, 100 → bright. Reading 0x4c afterwards returns the value set (`01 32` after setting 50).
- A **240×240 baseline JPEG (4:4:4, quality 85)** sent via `02 45` displays correctly and upright (the `^` mark is at the top): 18,982 bytes in 61 reports.
- **Frame rate:** 240×240 JPEGs of about 16 reports each (~5 KB) were shown smoothly at 10, 25 and ~70 fps, the last being as fast as hidapi could write. Median write time was 5 ms per frame. Animation is therefore limited by encoding, not by the module.

## Unknown
